# Semantic provider southbound request boundary

Candidate prerequisite; not wired into an HTTP adapter or deployed routes. No network calls or policy changes.

The current live inventory places Semantic on an internal Docker backend network, APISIX on internal backend/control networks and Caddy also on an edge network. A separate running southbound container was not observed. An internal Docker network is not evidence of a complete PET egress/default-deny policy. Reuse the current APISIX product and existing trust/materialization helpers; preserve northbound routes. Southbound service authentication, TLS, isolated control state and egress policy need explicit installation bindings and acceptance.

`tools/semantic_provider_boundary.py` accepts exactly the six bounded SPARQL read patterns currently generated by Semantic's SchemaGovProvider. It enforces exact form fields, request and intent limits, escaping and the fixed result bound. Arbitrary query statements, SERVICE clauses outside a literal, updates, endpoint overrides and duplicate fields are rejected. Escaped text mentioning query keywords remains data. This is technical request validation; Semantic still owns artifact matching and human semantic choices.

Candidate IRIs must match explicit installation-owned namespace prefixes. They are identifiers for a bounded retrieval at a registered provider endpoint; they must never be handed to an HTTP client or recursively dereferenced. Fetch adapter implementation and response/snapshot completeness checks are pending. The code validates HTTPS provider endpoints supplied by trusted installation configuration without resolving them or claiming network admission. Host, port, path, namespace prefixes, TLS references, network names and workload identity are parameters, with no laboratory defaults.

Deployment gates remain open: isolated southbound configuration and adapter wiring; bound service account and scopes/policy; provider and IAM allowlist/DNS/TLS/response limits; no credential propagation to external providers; caller/tenant-aware MCP command and read receipts; migration-aware Semantic job rollout; provider positive and negative acceptance; human-only adoption/review/publication. Existing semantic READ receipts cannot authorize commands or adoption. No source ingestion/replay, scheduler change, or policy publication is part of this change.

Ten focused tests include the six supported patterns, escaped text, injection/update/SSRF inputs, duplicate/malformed parameters, limits and custom provider domains/ports/paths. The PR tracks CI results. Full owner-to-Gateway-to-provider acceptance is not established by unit tests.
