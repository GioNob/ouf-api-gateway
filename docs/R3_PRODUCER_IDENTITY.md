# R3 authenticated operational producers

## Ownership and authentication

The Gateway now has a runnable private Java 21 producer in `operational-owner/`,
using the existing Gateway incident SQLite store and the **unchanged shared Java
Authorization SDK 1.2.0**. SDK sources are mirrored with their original checksum
manifest from Ingestion's pinned Authorization SDK; no second policy evaluator,
IAM directory or request-time remote PDP was added. Gateway continues to own only
its operational evidence, not ingestion/domain records. The Python owner class
remains a reference/test adapter; the Java host is the deployment target.

After OIDC/workload and human-delegation validation, the summary APISIX Lua
adapter signs `X-OUF-Operational-Receipt` for the two producer hops. The HMAC
SHA-256 input is `ouf-operational-owner-v1.` plus base64url JSON. The 30-second
receipt binds the exact forwarded body SHA-256, method, producer path/capability,
issuer, audience, workload, tenant, original subject/client, ACR, canonical IAM
roles/scopes and policy decision reference. It is separate from the human token
and from the MCP delegation. Producers cannot trust unsigned identity headers.

Keys are distinct per producer: `INGESTION_SUMMARY_RECEIPT_KEY` and
`GATEWAY_SUMMARY_RECEIPT_KEY` are each 64 hexadecimal characters (used as ASCII
HMAC key bytes, matching existing Gateway receipt conventions). Expose those
names through the APISIX Nginx environment. Mount the matching value read-only
only in its corresponding owner. Do not reuse the Authorization-owner or MCP
human-delegation key. Missing or invalid keys fail closed; none are committed.

The servlet filter verifies the receipt before creating `TrustedPrincipal`, then
uses the local shared SDK snapshot to require the producer capability with
TENANT_OPERATIONAL detail and the exact decision reference. Ingestion additionally
uses its existing `operations.status.read` policy for each source/result. AMR or
authentication-age constraints cannot be satisfied by invented claims: absent
claims fail those constraints. Policy refresh remains the SDK's governed ACTIVE
bundle flow; an unrefreshed file eventually fails closed at max staleness.

## Build and configuration

Build the pinned SDK, then `mvn -f operational-owner/pom.xml verify`. The resulting
Spring Boot JAR runs on port 8081 and can be packaged with the module Dockerfile.
The SDK tests classifier must not be present in that runtime JAR.

Both Java producers require these properties (there are no permissive defaults):

- `ouf.summary.receipt-key-file`: read-only mounted producer-specific key.
- `ouf.summary.tenant-id`: installation tenant. Gateway store is single-tenant.
- `ouf.summary.issuer`, `audience`, `workload`: same resolved installation binding
  used by the APISIX materializer.
- Existing `ouf.authorization.*` bundle reference/refresh settings: exact bundle
  ID/version/hash, then ACTIVE refresh with a bounded freshness window.

Gateway also requires `ouf.summary.database-file`, an **existing** incident store.
It opens SQLite with `mode=ro`; missing files/tables return unavailable, never
an invented healthy empty store. Counts, restricted visibility and catch-up page
are read in one database snapshot. Source filters are unsupported for Gateway;
its fixed API accepts only limit/since. Ingestion enforces the requested source
before the database query and preserves tenant/source filtering for returned rows.

The producer SDK capabilities are `ouf.gateway.operations.summary` and
`ouf.ingestion.operations.summary`, READ, HUMAN, scope `operations.status.read`,
resource type `capability`, permitted detail TENANT_OPERATIONAL. Ingestion also
requires its local `operations.status.read` operational/source grants. These are
requirements for the existing governed policy workflow, **not grants created by
this code**. Revoked IAM roles must continue to yield denial.

## Verification and release boundary

Java tests consume receipts generated by the actual Gateway Lua code, covering
role removal, missing receipt, body tampering, expiry, wrong tenant/owner and
policy version/revocation. Ingestion's PostgreSQL runtime test exercises the full
servlet filter, shared SDK, source check and real incident query. Gateway CI boots
the real Java producer behind real APISIX and an isolated synthetic OIDC issuer:
allowed role, same subject without role, forged direct headers and protected-row
redaction are checked. These test credentials/policies are fixtures only.

The exact same receipt filter source and Lua-produced vectors are mirrored in
Ingestion and Gateway; pairwise CI must detect drift. No deployment, role
assignment or policy publication is performed. Installation acceptance still
requires the actual mounted keys, ACTIVE policy refresh, network isolation/TLS,
compatible image versions and approved grants. Rotate keys and deploy owners
before enabling the summary profile; retain the previous route snapshot for
rollback. End-to-end lab evidence is not evidence from the live OUF installation.
