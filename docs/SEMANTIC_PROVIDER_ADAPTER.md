# Semantic provider transport admission and TLS adapter

Candidate component in existing Gateway PR #56. Not installed and not an acceptance of provider discovery, kernel egress or a production deployment. The source endpoint, role/container/network bindings, domain, port, certificate/trust paths, issuer/audience/workload/tenants, route IDs/paths and namespace boundaries are installation parameters. No laboratory installation address is a runtime default.

## Request and authority boundary

`materialize_semantic_provider.materialize(existing, config)` adds precisely one POST search route and one GET fetch route to an existing snapshot. It preserves existing route objects and refuses collisions. It emits only a plan; there is no Admin API write. The methods match the current Semantic provider's actual native HTTP contract. Both routes retain OIDC signature/JWKS validation, TLS validation for IAM, audience checks, required workload scope, SERVICE actor, exact workload, allowed tenant list, bounded body and explicit local rate limit. A post-OIDC Lua guard signs original method + request URI + body bytes, not a reconstructed form. No proxy rewrite changes the signed target.

The purpose-separated `ouf-semantic-provider-owner-v1` receipt carries the installation, issuer, audience, workload, tenant, subject, SERVICE actor, granted transport scope, request SHA-256 and a lifetime at most 30 seconds, capped by the JWT expiry. The HMAC key uses the project's existing convention of 64 hexadecimal text characters as key bytes. **Provision a new provider receipt key, separate from OAuth client credentials, MCP delegation and semantic READ-owner keys.** The Gateway environment exposes only this technical key to the Lua runtime. The adapter receives the same key from a private read-only file. Key values must never appear in command arguments, public output or repository content.

Gateway rewrite strips caller `X-OUF-*` headers. After OIDC admission, the access guard discards forged identity/proof headers, Authorization, Cookie and OIDC token/userinfo headers before forwarding the newly signed receipt. At the adapter, an absent, duplicate, forged, expired, wrong-context or byte-mismatched receipt is denied before provider calls. A forwarded Authorization header is rejected. These receipts grant fixed READ-only transport; they cannot approve, adopt, publish, ingest or modify application authorization. Bounded READ receipts may be replayed until expiry; they are not mutation receipts or durable idempotency keys. Signature validation is not token revocation proof.

## Bounded listener

`python3 -B -m tools.semantic_provider_adapter --configuration <installed-json-file>` starts only with complete configuration and a non-root user. The receipt and TLS private key must be owned by that user, private regular files, single-link and non-symlink. The listener requires a configured certificate/private key and TLS 1.2 or later. There is no plaintext fallback. Linux fork workers have a configured maximum (1–16), a finite backlog and a complete request deadline including TLS handshake, header receipt, body, provider exchange and response write. Nested relay deadlines preserve the remaining outer budget.

Exact routes, one Content-Length, bounded body/target and supported media are enforced. Transfer/content encoding, Expect, ambiguous/incomplete body and extra query grammar fail closed. Early framing rejection can close the connection without draining ambiguous input; no reusable connection is left. Errors and logs expose no receipt, bearer, query, candidate URI, provider body, key, configuration path or traceback. The relay uses the already tested fixed registered HTTPS provider, approved DNS answers/numeric connect, SNI/certificate validation and bounded response controls. Fetch returns only outgoing asserted subject triples, explicitly marked `X-OUF-RDF-Scope: OUTGOING_ASSERTED_SUBJECT_TRIPLES`; it is not ontology/import/blank-node closure or a complete adopted artifact.

The materializer requires a single explicit HTTPS adapter host/port, explicit upstream hostname, `tls.verify=true`, fixed finite timeouts and no upstream retries. The pinned APISIX runtime must support and enforce these settings, including a negative certificate hostname test. This must be proven rather than inferred from current/latest documentation. Real fixture validation uses APISIX 3.18.0; live image compatibility remains a separate gate.

## Configuration contract

Adapter JSON has exactly: `listenAddress`, `listenPort`, `maxWorkers`, `requestTimeoutSeconds`, `searchPath`, `fetchPath`, `provider`, `admission`, `receiptKeyFile`, `tlsCertificateFile`, `tlsPrivateKeyFile`. `provider` uses `ProviderBinding` field names (`endpoint`, `namespace_prefixes`, optional governed `allowed_cidrs`/`ca_file` and technical bounds); `admission` uses `AdmissionBinding` field names (`installation`, `issuer`, `audience`, `workload`, `scope`, `tenants`). TLS trust for the external provider and the internal adapter is explicit. No credential from a human/model is an authority header.

Materializer config has exactly: `installation`, `issuer`, `audience`, `workload`, `scope`, `tenants`, `searchPath`, `fetchPath`, `searchRouteId`, `fetchRouteId`, `receiptKeyEnvironment`, `oidcSecretRef`, `upstream`, `rateLimit`, `maxRequestBytes`. Upstream requires `type=roundrobin`, `scheme=https`, one `nodes` host:port with weight 1, `pass_host=rewrite`, `upstream_host`, `tls.verify=true` (optional explicit `tls.ca_certs`), and bounded `connect/send/read` timeout. Rate limit has explicit `count`, `time_window`, `key_type=var`, `key=remote_addr`, `policy=local`, `rejected_code=429`.
