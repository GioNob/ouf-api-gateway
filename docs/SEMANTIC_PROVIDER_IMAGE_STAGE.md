# Provider transport image packaging and staging

Candidate packaging in Gateway PR #56; a staged image is not a release. Operator evidence confirms the already-running APISIX binary is **3.18.0**, matching the real CI TLS/admission fixture. Its installed trust, isolated southbound role and egress policies still need their own evidence.

`Dockerfile.semantic-provider` uses an explicitly digest-pinned Python 3.13 base; no runtime image/tag/domain/port/UID/GID is a default. Build arguments require source commit, build-payload checksum and non-root UID/GID. The context copies only the five reviewed standard-library transport/admission modules, no tests, repository credentials, configuration, certificate or secret. Public source permissions are set before switching user. Runtime starts only with an operator-supplied configuration argument. Read-only filesystem, dropped capabilities, no-new-privileges, bounded PIDs, private mounts and network policy are installation requirements, not implicit Dockerfile guarantees.

`scripts/stage_semantic_provider_adapter.py --mode plan|apply|verify` requires explicit Gateway container/ID/version, source origin/commit, base digest, image tag, runtime UID/GID and snapshot root. Plan reads version/configuration/image metadata without download or write. Apply refuses reused directories/tags, creates a private root-owned snapshot, downloads only the pinned minimal build payload and checks every SHA-256. Redirects and changed bytes are refused. OCI build runs with `--network=none --pull=false` from the selected pre-acquired digest. Image revision/payload labels, user, entrypoint and image ID are verified; sensitive Gateway inspect values are only hashed, never saved/printed. Selected live Gateway configuration/running identity must remain identical before/after build. Verify checks the saved private receipt and actual image; it never rebuilds.

No runtime container creation/start/switch, secret read/mount, route or IAM write, database migration, application policy publication or provider call is implemented by this helper. Docker's build workers/cache and the staged image are expected build artifacts, not deployed OUF services. A failed/interrupted apply preserves the intent/context; do not blindly rerun or overwrite the stage. If a success receipt exists, use verify with exactly the same bindings. If it does not, reconcile the existing intent/image state before selecting another root or tag.

Base acquisition is explicit: an operator may select a Python 3.13 image, acquire it and pass its resolved repository digest. The mutable acquisition tag is not used in FROM; the final base digest is recorded. Digest integrity alone is not publisher signature/provenance acceptance. Software/registry origin, mirror and supply-chain approval stay part of installation policy. The CI fixture selects `python:3.13-slim`, resolves its digest, then builds and records that immutable digest; that selection is a fixture input, not a production default.

Local staging tests cover read-only plan, source/base/tag/runtime-ID guards, identity/version/drift, minimal offline build arguments, private intent/receipt, no overwrite/blind retry, source hash/redirect rejection, staged image contract and secret redaction. The dedicated CI staging job runs as root so ownership/ancestor/verify guards are actually tested. The separate container CI builds the exact minimal image, starts its real native entrypoint as non-root with read-only root, capabilities dropped and private read-only mounts, verifies TLS/direct denial, and proves that a valid receipt with invalid grammar stops before DNS/provider exchange. It is intentionally not a provider positive test. The existing separate real APISIX fixture proves OIDC -> signed receipt -> TLS adapter with controlled exchange. CI host networking is a fixture convenience and proves no production egress isolation.
