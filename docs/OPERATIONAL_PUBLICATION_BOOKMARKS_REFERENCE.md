# Owner publication bookmark reference

This private SQLite reference follows [platform resilience policy v3](https://github.com/GioNob/ouf-deploy/blob/main/docs/OUF_RESILIENCE_POLICY.md), [cursor/consultation design](https://github.com/GioNob/ouf-deploy/blob/main/docs/OUF_OPERATIONAL_CURSOR_DESIGN.md), Gateway PET1.5 and MCP PET1.4 operational awareness.

Profile: `ouf.owner-publication-bookmark.v1`. A coverage bookmark survives the thirty-minute owner page session and binds stable principal/tenant/actor/workload issuer/audience, owner policy and immutable state filter. Login/authentication-context changes alone do not erase it. Every start/page/resume requires a fresh owner-local collection evaluator; every item requires the current row evaluator. The host evaluator must verify exact authenticated identity, policy reference, platform resource scope and RESTRICTED_OPERATIONAL detail. The constructor has no default grant and this primitive is not wired to a public route or MCP tool.

Resume selects incidents with later committed publication revisions, taking their latest captured state at the new watermark. An old occurrence timestamp does not hide a newly committed change. SQLite's serialized writer/commit order justifies this reference revision; the same argument does not apply to PostgreSQL bigserial. Ingestion must use its pending publication ledger and committed tenant clock in its separate implementation.

Saved state filters remain immutable; callers may choose a bounded page size but cannot replace state, inject timestamps/revisions or choose an endpoint. Time-window queries are deliberately not accepted by this coverage primitive. Expired bookmark or an owner history floor beyond its boundary returns an explicit410 history gap, never an empty successful catch-up. A history floor cannot rewind. The actual history compactor remains OPEN; the floor is an owner maintenance contract, not authority to delete immutable incident history.

A successor bookmark is issued only after the complete captured page chain has recorded non-redacted reads, with the completeness check repeated atomically inside the metadata issue transaction. Partial/missing pages cannot issue it. Parent bookmark lineage and filters are immutable; retries issue the same token. All authorization and item callbacks run outside write transactions. Only bounded local metadata writes occur under SQLite's finite lock timeout.

Bookmark storage is metadata-only: no incident payload, credential or cached grant. Reviewed finite profile:90-day expiry,512 bookmarks/principal,4,096/tenant,32,768 globally. One expired record is cleaned per issue; live positions cannot be silently deleted/replaced. Exhaustion rejects new issuance, while old bookmark replay and independent incident writes remain available. This profile is an OUF reference choice, not an AWS-prescribed default. The page/session/row quotas of the existing owner cursor remain in force and response size remains512KiB.

`publicationBookmark` is a read position. All pages retain `consultationRecorded=false`. It proves neither client delivery nor that an operator saw the page, and it never takes ownership of/resolves an incident or renews a quarantined job. MCP checkpoint advancement still requires the separate reviewed confirmation capability, explicit client receipt, parent-vector binding and expected-version CAS. Current urgent OPEN incidents must be read independently from changed-since coverage.

Qualification: late publication with old times, resume after page expiry/store reopen/new login, full versus redacted page chains, replay, current revocation/identity/policy isolation, timestamp/revision rejection, immutable metadata, expiry/history gaps, monotone history floor and finite persistent capacity with independent incident writes. Native Python/full Authorization/APISIX gates remain required.

OPEN: actual Gateway host/SDK wiring, Ingestion publication bookmarks, governed producer/global schemas, MCP vector/client confirmation/checkpoint, populated target/HA/history compaction and retention. No route is broadened here, and no migration, target restart, email or consumed R9/R10 activation is performed.
